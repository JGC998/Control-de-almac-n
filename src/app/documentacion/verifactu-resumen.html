Veri*Factu

Sistema de Verificación de Facturas — AEAT

Mayo 2026 · Fuente: RD 1007/2023 + Orden HAC/1177/2024 + RDL 15/2025

¿Qué es Veri*Factu?

Es la obligación legal de que el software de facturación (SIF) genere registros de facturas con un hash SHA-256 encadenado (cada factura incluye el hash de la anterior), garantizando que no se pueden alterar o eliminar facturas sin dejar rastro. Opcionalmente, esos registros se envían a la AEAT en tiempo real.

Lo que aplica a CRM Taller: Solo afecta a las FACTURAS. Los presupuestos, pedidos y albaranes quedan completamente fuera del sistema VeriFactu. Una factura puede nacer de un albarán o directamente de un pedido — no importa el origen, lo que importa es el documento factura.

⛓️ El encadenamiento de hashes

Cada factura emitida incluye el hash SHA-256 de la factura anterior. Esto forma una cadena: si alguien modifica o borra una factura intermedia, todos los hashes siguientes quedan invalidados. Es el mismo concepto que una blockchain.

F-001
hash: 3C464D…
→
F-002
incluye hash F-001
→
F-003
incluye hash F-002
→
F-004 (nueva)
incluye hash F-003

Los campos que entran en el hash (en este orden exacto): IDEmisorFactura, NumSerieFactura, FechaExpedicionFactura, TipoFactura, CuotaTotal, ImporteTotal, Huella (anterior), FechaHoraHusoGenRegistro

📱 El código QR en la factura

Cada factura debe llevar un QR impreso con esta URL (mínimo 30×30 mm):

https://www2.agenciatributaria.es/wlpl/TIKE-CONT/ValidarQR
  ?nif=B12345678
  &numserie=2024F001
  &fecha=15-01-2024
  &importe=121.0

Y el texto visible: "Factura verificable en la AEAT"

Librería Node.js: npm install qrcode → QRCode.toDataURL(url, { errorCorrectionLevel: 'M', width: 150 })

🗺️ Plan de implementación — Fase D

Fase D1 — Hash + QR (sin envío a AEAT) · Fecha objetivo: sept 2026

  • Nuevos campos en Factura: tipoFactura, huella, huellaAnterior, fechaHoraGenRegistro, estadoEnvioAeat
  • Servicio src/lib/verifactu.js: calcularHuella(), construirURLQR(), generarXMLRegistroAlta()
  • QR en el PDF de factura + texto "Factura verificable en la AEAT"
  • Configuración del emisor (NIF, nombre) en /configuracion
  • El hash se calcula en el momento de emitir la factura (BORRADOR → EMITIDA)

Fase D2 — Exportación XML para subida manual a AEAT · Fecha objetivo: nov 2026

  • API GET /api/facturas/exportar-aeat → genera RegFactuSistemaFacturacion.xml con facturas pendientes
  • Botón "Exportar XML para AEAT" en la vista de facturas + badge de estado (PENDIENTE / EXPORTADO / CONFIRMADO)
  • Campo para registrar el CSV de confirmación que devuelve la AEAT
  • El certificado FNMT lo usa el usuario en su propio navegador — no toca el servidor
  • Sin SOAP, sin colas, sin gestión de certificados en el servidor

Fase D3 — Rectificativas R1–R5 · Fecha objetivo: dic 2026

  • UI para crear factura rectificativa desde una factura emitida
  • Selección tipo (R1–R5) y modalidad (S=Sustitución / I=Diferencias)
  • XML con elemento <FacturasRectificadas> que referencia la original

✅ Flujo de envío a AEAT — DECIDIDO: exportación XML manual

En lugar de SOAP automático (complejo, necesita certificado en servidor), el flujo es:

1. Emitir factura → hash calculado → PDF con QR generado → inmutable
                                              ↓ (cuando el usuario quiera)
                              Botón "Exportar XML para AEAT"
                                              ↓
                              Descarga verifactu-2024-01.xml
                                              ↓
                              Usuario sube .xml en portal AEAT con su certificado FNMT
                                              ↓
                              AEAT devuelve CSV de confirmación → se registra en CRM

Ventajas de este enfoque

Sin certificado en el servidor · Sin SOAP · Sin colas · El usuario controla cuándo envía · Mismo XML que el SOAP (válido legalmente)

⚠️ Problemas que podemos encontrarnos

ProblemaImpactoMitigación
Zona horaria incorrecta en timestamp Alto — el campo entra en el hash; si el timezone es incorrecto, el hash falla la validación AEAT Usar siempre Europe/Madrid (Intl API de Node.js) — resuelve automáticamente +01:00 invierno / +02:00 verano.
Ceros decimales en importes Alto — 100.00 y 100 producen hashes distintos Normalizar siempre con parseFloat(n).toString() antes de concatenar en la cadena del hash. Especificado en la ley.
Facturas creadas antes de activar VeriFactu Bajo — no tienen hash La primera factura tras activar VeriFactu marca <PrimerRegistro>S</PrimerRegistro>. Las anteriores no necesitan hash retroactivo.
Cambio de normativa / nuevos XSD de la AEAT Medio — pueden cambiar campos obligatorios o validaciones Toda la lógica VeriFactu en src/lib/verifactu.js aislado. Revisar la web de la AEAT antes del plazo (ene 2027).
XML rechazado por la AEAT (errores de validación) Medio — la AEAT devuelve un XML de error con código Probar primero en preportal.aeat.es. El fichero Validaciones_Errores_Veri-Factu.pdf lista todos los códigos de error posibles.
Descartados: Race condition (mono-usuario, imposible) · Certificado en servidor (flujo manual, el certificado solo lo usa el navegador del usuario)

💡 Sobre pedidos que no llegan a factura

Como comentaste: muchos pedidos de cliente no van a generar factura. Esto es perfectamente normal y no afecta a VeriFactu. El sistema solo entra en juego cuando se crea una Factura (modelo Factura en BD). El flujo puede ser:

  • Pedido → Albarán → Factura ✅ (pasa por VeriFactu al emitir la factura)
  • Pedido → (sin factura) ✅ (no le afecta VeriFactu)
  • Pedido → Factura directa ✅ (también pasa por VeriFactu)
Conclusión: Implementar VeriFactu solo dentro del módulo de Facturas es correcto y es exactamente lo que hace la Orden HAC/1177/2024. Presupuestos, pedidos y albaranes quedan completamente fuera.

✅ ¿Es asequible implementar todo esto?

Fase D1 (hash + QR): Sí, muy asequible. Es básicamente:

  • Una función de 20 líneas (calcularHuella)
  • Una función de 10 líneas (construirURLQR)
  • npm install qrcode
  • 4 campos nuevos en el modelo Factura
  • Modificar el PDF para añadir el QR

Estimación: 1 sesión de trabajo

Fase D2 (envío AEAT): Asequible pero requiere más trabajo:

  • SOAP con Node.js (npm install soap)
  • Gestión del certificado .pfx
  • Cola de envíos + reintentos
  • Nuevo modelo RegistroVeriFactu

Estimación: 2–3 sesiones de trabajo

Recomendación: Hacer D1 primero (hash + QR en PDF, sin envío). El usuario puede emitir facturas conformes con QR antes del plazo de 2027. El D2 (envío real a la AEAT) se puede añadir después sin tocar el modelo de datos ni el PDF.
